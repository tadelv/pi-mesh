# Milestone 5 implementation plan — a-team handoff packets

Status: implementation plan, **not** evidence of working hardware. ADR 0016 is accepted after council review. Follow `tasks/milestone-5.md` in issue order. The parent owns decisions, browser/hardware verification, git and final UX review. A-team workers make bounded edits, do not commit; reviewers read the diff and check each named clause for false positives. Consult `AGENTS.md`, `docs/GOTCHAS.md`, ADRs 0008/0011/0013/0015 and `docs/PROTOCOL.md` before changing the execution path.

## Answer to the browser-test decision (M5-2)

Choose **`@playwright/test`**, as the one new dependency, with Chromium installed separately in CI (`pnpm exec playwright install --with-deps chromium`). The dashboard is inline HTML/CSS/JS in `packages/control-plane/src/dashboard.ts`: Vitest's source-string checks cannot run the DOM, and a simulated DOM cannot establish browser focus, native forms or asynchronous rendering. Test the actual page served on `127.0.0.1` by `createControlServer`; intercept `/api/*` only where a controlled response order is needed. Intercepts must check path, method, dashboard-token header and request body, and reject an unexpected request rather than returning generic success. Keep existing Vitest agent/API tests for gate and wire behaviour; Playwright is not their replacement.

Add a `test:browser` root script and a small `playwright.config.ts` (Chromium only, bounded timeout, traces on failure, no snapshot updates in CI). Browser specs live outside `packages/*/test` so Vitest does not collect them. Run build before browser tests when importing `dist`; make the fixture start/stop its loopback server and close its temporary SQLite store. Run in CI after build and install the browser; do **not** put the browser suite behind a local-only optional command. Verify install/runtime on Node 22 and Linux as well as the developer machine. State the harness choice and limits in M5-2's recorded decision (a short ADR or a dedicated decision paragraph in the milestone; no second dependency for a test DOM).

What Playwright **does** cover: actual DOM ownership under delayed requests, focus after navigation/re-render, keyboard-only controls, semantic `role=status`/live-region attributes and updates, light/dark and narrow/wide rendering, inline confirmation and double-click prevention. What it **does not** prove: actual assistive-technology speech (manual screen-reader pass), actual Pi prompt delivery (real agent + hardware transcript), or transport policy (existing server tests). If focus/announcement behaviour is not implemented in M5-2, explicitly list it as uncovered rather than treating an attribute check as proof of spoken output.

## Packet 0 — M5-1 ADR before any UI or harness work

Accepted decision: `docs/adr/0016-session-prompt-identity.md` (council-reviewed). The agreed operator choices are captured there:

- Resolve `(agent_id, session_id)` using matching running `state.jobs` rows for that agent; never guess from project, name, row order or PID. If multiple running jobs claim the session, require an explicit operator choice of job and confirmation, with job ID, PID, project and start time shown; do not preselect. A choice identifies a **job**, not proof that its conflicting session claim is right. Stopped rows do not win over a running one.
- Make `jobs_synced_at === null` (including post-restart or post-spawn invalidation) an explicit unknown state, not a claim that the cache is live. Require a confirmed jobs sync before enabling prompt; a timestamp alone does **not** establish present reachability. `stale` means transcript read failed for any reason, **not** proof the agent is offline; label it “could not verify.” A 502 means the agent call failed (including malformed replies), not necessarily that the machine is offline.
- Gate the control on the **selected** session, advertised `controls.steer`, an unambiguous running job, and execution transport permitting the route (ADR 0014). Distinguish never synced, no matching job, exited job, opt-out, unreachable, ambiguous job and insecure transport in the UI. Re-check the selected owner and eligibility on submit; let the agent remain the authority over its current jobs and gate.
- Use the existing `POST /api/agents/:peerId/steer {job_id,message}`. On 200 `{ok:true}` say **accepted / checking transcript**, not delivered. Within 15 seconds, report a matching newly appended user turn as **observed, origin not verified**; otherwise say unconfirmed and retain the draft. Do not treat the 200-entry page as exhaustive; do not require expensive full-history scans. No new grant or execution route.
- Decide a maximum in **UTF-8 bytes** (suggestion: 4096); the agent should reject over-limit direct skill requests with `-32602`, while the UI prevents sending over-limit text and retains the draft. Do not rely only on `maxlength` (UTF-16 units) or a client-only check. If this is a protocol-visible bound, update `docs/PROTOCOL.md` in M5-3.

ADR acceptance checklist (met by the council revision): every M5-1 case has a knowable reason; no statement implies a synced mirror is authoritative, `stale` means unreachable, or a matching turn proves attribution. Refusal `-32102` and agent-call failure `502` remain distinct. Bounded re-reads are allowed, not dashboard streaming; do not let a worker invent missing policy.

Retire the old jobs-list Steer form when the session composer lands (ADR 0016); keep job stop/abort.

UX contract: keep the transcript a readable log, not chat bubbles with imaginary live replies. A compact composer under the selected transcript: clear heading identifying target agent/session, labelled multiline input, message byte count, Send button, and a reason in the same location when sending is unavailable. No focus-stealing on polling, no whole-transcript live-region announcements; announce short status changes separately. Preserve the draft on `-32102`, `-32004`, `-32103`, `-32602`, `502`, 403, missing job or wrong selection; clear it only on confirmed success under the accepted ADR. Distinguish “agent refused (code …)” from “agent call failed (502)” from “execution transport is insecure”. Do not infer offline from `stale`. A pending request cannot silently migrate to a newly selected session. A successful API response alone is not a delivered turn: visibly check for a new matching user entry in the selected session, bounded as ADR specifies; say origin unverified even on a match. Test an identical turn from a competing writer and an overrun of the 200-entry tail as **unconfirmed**, never as delivery or proof of non-delivery. Do not claim streaming.

Browser clauses (strict intercepted request bodies) plus agent integration: only selected agent+job gets a single POST; no POST for absent/offline/unknown capability or **unresolved** ambiguity; two running matches require an explicit job choice and confirmation, and the body must carry that chosen job ID; refusal keeps text and code; 502 keeps text with transport status; switch sessions mid-flight and ensure neither draft/result appears under B; simulate transcript growing after acceptance and assert it is shown. Mutate each ownership/refusal/delivery clause and see the named assertion fail. Existing `packages/control-plane/test/execution.test.ts` remains the gate/agent-path positive control; for actual acted-on turn M5-5 must use Pi, not a 200-shaped stub.

## Packet 4 — M5-4 start without blocking dialog

Worker scope: `packages/control-plane/src/dashboard.ts` + focused browser tests; split out any non-UI API changes only if cached data proves insufficient. In the per-agent section, use a native `<datalist>` of **full project values** seen in `state.sessions` and `state.jobs` for that agent, de-duplicated; display basenames only as secondary labels. Keep free text for a first-time agent, with “No projects seen here yet; enter one” rather than an empty suggestion list masquerading as history. Do not assume a project name equals a directory; preserve the existing optional cwd input and agent validation. Replace `window.confirm()` with an inline confirmation state that names agent and project; first action exposes review, explicit second action starts, Cancel keeps fields. While pending disable the final action **synchronously**, before awaiting the route; keep form values stable through refresh. On success display `job_id`, `session_id`, `pid` and an Open session action that works when the session appears in the cache (otherwise say “sync to find session”, not a broken link). On refusal retain content and show code/reason inline, including 502/403 distinctly.

Browser tests: projects from one agent never bleed into another; first-time fallback works; no `window.confirm` called; confirmation requires deliberate second action; two immediate submits send exactly one request, mutation of the guard fails the “single start” clause; refusal preserves fields and retry works; successful result shows identifiers and opens only the matching session when available. Avoid a generic stub that returns any shape: assert exact POST `{project,prompt,cwd?}`. Parent verifies the gate and process-machinery scan still pass.

## Packet 5 — visual/interaction polish (after both flows work)

Parent is design director, a-team worker implements one focused `dashboard.ts` pass and reviewer audits states. Start from `DESIGN.md` and `PRODUCT.md`: Pi-like monospace transcript, no external assets, light/dark tokens, tool payloads collapsed, mobile sidebar. Do **not** add a framework, icon/font CDN, chart or a second design system. Proposed hierarchy: a restrained fleet topbar; scannable sessions with agent and updated time; wide transcript reading column; composer directly following that session's log; a separate clearly titled agent-management area for pair/start/jobs. Design the **states**, not just the happy screenshot: unauthenticated, empty fleet, syncing, cached/offline, working/refused, long paths and IDs, ambiguous session, narrow phone. Use a single action accent; reserve warning/error colours for operational risk, not decoration. Make copy about execution precise (token + local opt-in + transport); never hide refusal behind disabled styling alone.

Proposed screen hierarchy (not a chat app):

```text
Pi Mesh     [connected / last sync]                         [Sync] [Pair]
┌ Sessions / filter ────────┬ Session name                       agent · project ┐
│ Agent A                   │ [cached/offline or live-job status, when relevant] │
│ ● Session name   2m ago   │                                                │
│   another session          │ Transcript: user / assistant / collapsed tools  │
│ Agent B                   │                                                │
│ …                         │ [older entries]                                 │
│                           │ Prompt THIS session (or exact reason unavailable)│
│                           │ [multiline draft]   [Send] [delivery status]     │
├ Agent management ─────────┴────────────────────────────────────────────────┤
│ Agent A: capability + freshness · [Start session] · jobs [Stop] [Abort]  │
└────────────────────────────────────────────────────────────────────────────┘
```

At narrow widths, keep Sessions reachable without scrolling through the whole transcript and place controls in document order beneath their heading; do not float a composer that obscures history. Give transcript text more readable line-height/size than job metadata (the current 12px/18px base is a design choice, **not** an untouchable constraint: revise `DESIGN.md` if a tested 14px reading scale wins). Prefer alignment, spacing and carefully differentiated surface colours over decorative gradients. The central UX payoff is *confidence*: at a glance the operator can tell which session is selected, whether its job is actually steerable, whether a prompt was merely accepted, and whether a new turn appeared.

Acceptance: capture and inspect screenshots at ~390px and ~1440px, light and dark, with real-looking long transcript/tool content and at least one refusal and empty/offline state. Verify keyboard-only order, visible focus, labels, `aria-live` status changes without announcing an entire transcript, 200% zoom, reduced-motion preference and legible contrast. Playwright can check structure, focus, overflow and selected screenshots; human review decides whether it feels coherent. Manual screen-reader spot-check for actual announcements (Playwright cannot hear them). Iterate on screenshots with the parent rather than ask an implementation worker to independently declare the design good. Update `DESIGN.md` / `PRODUCT.md` once the approved design is real, not in advance.

## Parent validation and delegation rhythm

For each bounded worker packet: fresh a-team worker, no staging/commit/push; inspect `git status` and diff immediately, run its focused test and red→green mutation; then run `pnpm -r build`, `pnpm typecheck`, `pnpm -r test`, `pnpm test:browser`, `pnpm -r lint`, `pnpm format:check`. Supply the resulting diff and transcripts to a fresh read-only a-team reviewer. Fix blocking findings, rerun focused checks, and only then advance. CI's Linux/Node 22 outcome and actual browser screenshots are independent evidence. Do not call M5 complete without the hardware transcript. Recommended order: ADR → browser harness → agent bound → prompt UI → start UI → visual pass → docs/hardware. Split any packet that exceeds one source file and one focused test; don't run dependent UI packets concurrently.
